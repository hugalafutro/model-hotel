# 📜 Request Logging

Every request that passes through the proxy is logged with detailed telemetry. This helps you understand performance, identify bottlenecks, and debug issues.

## What Gets Logged

> [!IMPORTANT]
> The proxy records metadata only - **never the prompt content or response text**.

All fields are written to the `request_logs` PostgreSQL table.

### Request Log Schema

| Column | Type | Description |
|--------|------|-------------|
| `id` | UUID | Primary key, generated by the proxy before the row is written |
| `request_hash` | TEXT | Random 16-character hex request identifier (8 random bytes from `crypto/rand`). Not content-derived. |
| `model_id` | TEXT | The requested model (e.g. `deepseek/deepseek-chat` or `hotel/gpt-4`) |
| `provider_id` | UUID | Which provider handled the request. NULL until resolved, and set back to NULL if the provider is later deleted. |
| `virtual_key_id` | UUID | Foreign key to `virtual_keys` (NULL for anonymous and dashboard requests) |
| `virtual_key_name` | TEXT | Which virtual key was used. Retained even after key deletion for audit purposes. |
| `status_code` | INT | HTTP status for the request, rewritten across its lifecycle. See [Status code and error kind over a request's life](#status-code-and-error-kind-over-a-requests-life). |
| `error_message` | TEXT | Error text on failure, capped at 10,000 characters. Populated for upstream provider errors and proxy-internal errors (invalid model format, provider not found, etc.). Empty on success. |
| `error_kind` | TEXT | Machine-readable failure classification (migration `045`). NULL on success and on rows predating the column. See [Error classification and status codes](#error-classification-and-status-codes). |
| `streaming` | BOOLEAN | Whether the request used SSE streaming |
| `failover_attempt` | INT | Which attempt this was - `0` for the first try, incrementing with each failover |
| `resolved_model_id` | TEXT | The actual upstream model ID used (e.g. `z-ai/glm-4.6`). Written only for `hotel/` requests, where it differs from the requested `model_id` (e.g. `hotel/glm-4.6`); empty for direct provider requests. |
| `state` | TEXT | Request lifecycle state: `pending` → `streaming` → `completed` or `failed` |
| `endpoint_type` | TEXT | Endpoint family the request came through: `chat` (default), `messages`, `embeddings`, `rerank`, `image`, `tts`, or `stt`. Written at INSERT time; exposed in the Logs API, filterable via `?endpoint_type=`, and shown as a badge in the dashboard Logs page for non-chat requests. |
| `attempts` | JSONB | Per-attempt trail: one element per failover attempt, hedged probe and pre-request skip. NULL for rows predating migration `078` and for requests that never committed to a provider. See [Per-attempt trail](#per-attempt-trail). |
| `duration_ms` | REAL | End-to-end wall time (request start to response end) |
| `latency_ms` | REAL | Provider response time only (`duration_ms - proxy_overhead_ms`) |
| `proxy_overhead_ms` | REAL | Total proxy overhead (sum of all seven overhead phases) |
| `parse_ms` | REAL | JSON parsing and request validation time |
| `failover_lookup_ms` | DOUBLE PRECISION | Time resolving the failover group for `hotel/` requests (0 for direct requests) |
| `model_lookup_ms` | REAL | Time resolving the model entity, checking enabled status, building candidate list |
| `provider_lookup_ms` | REAL | Time finding provider record in database (excludes key decryption) |
| `key_decrypt_ms` | REAL | Time decrypting provider API key (first call per 10-minute cache window; subsequent calls near-zero) |
| `settings_read_ms` | DOUBLE PRECISION | Time reading runtime settings from cache (circuit breaker state, rate limits, etc.) |
| `dial_ms` | DOUBLE PRECISION | Full DNS + TCP dial time to the upstream provider (renamed from `safe_dial_ms` in migration 032) |
| `cache_hits` | JSONB | Per-component cache hit/miss flags (`failover`, `model`, `provider`, `key`, `settings`); `true` = prewarmed cache hit, `false` = miss, absent = not applicable |
| `response_header_ms` | REAL | Time until upstream HTTP response headers arrived (renamed from the old `ttft_ms` in migration 035, which had actually measured headers, not tokens) |
| `ttft_ms` | REAL | True time to first token (streaming requests only). Measured by the TTFT probe that reads ahead to confirm the first data chunk before committing the stream. |
| `tokens_per_second` | DOUBLE PRECISION | Streaming throughput (`completion_tokens / generation_duration × 1000`) |
| `tokens_prompt` | INT | Number of prompt tokens reported by the provider |
| `tokens_completion` | INT | Number of completion tokens reported by the provider |
| `tokens_completion_reasoning` | INT | Reasoning tokens (DeepSeek-R1, etc.). Written to DB and exposed in Logs API. |
| `tokens_prompt_cache_hit` | INT NOT NULL | Prompt cache hit tokens (DeepSeek). Defaults to 0. |
| `tokens_prompt_cache_miss` | INT NOT NULL | Prompt cache miss tokens (DeepSeek). Defaults to 0. |
| `owner_user_id` | UUID | Owning dashboard user, stored **only** for keyless rows (dashboard chat/arena); keyed rows resolve their owner through the key's current owner instead (migration 067) |
| `client_ip` | TEXT | Trusted-proxy-resolved client address, written at INSERT time (migration 073). NULL on rows predating the column. Shown in the dashboard Logs IP column and detail modal; see [Privacy](Privacy#ip-address-handling). |
| `created_at` | TIMESTAMPTZ | When the request was inserted (defaults to `now()`) |

There is no cost column. The row stores token counts and the model's identity; money is worked out afterwards from the model's per-million prices, so re-pricing a model changes what past requests are shown to have cost.

### Status code and error kind over a request's life

`status_code` is nullable and starts empty. The initial INSERT omits it, so a request that never received upstream headers stays NULL. Once headers arrive the row is updated with the upstream status (typically `200`) and moves to `state='streaming'`, so a long-lived stream reads `200` *while still in flight*.

How it ends depends on where the request failed:

- **Mid-stream failure:** rewritten to `0`, whatever the cause. Find these by `state = 'failed'` and `error_kind`, not by status.
- **Terminal upstream non-2xx (non-streaming):** the **upstream's own** status is kept (`500`, `429`, `401`, and so on).
- **All candidates exhausted with no forwardable response:** the proxy synthesises a truthful gateway code: `499` (client hangup), `504` (failover or retry timeout), `429` (every provider alive and at capacity), or `502` for everything else.
- **Rejected before any upstream attempt:** validation and authorization failures carry their own code (`400`, `404`, `403`).

`error_kind` is written alongside `error_message` and is the classification to filter on; the status alone cannot tell a busy provider from a broken one. The dashboard's "Interrupted" badge reads `error_kind`, falling back to substring-matching the English `error_message` only when it is NULL. The Prometheus `error_kind` label carries the raw value verbatim and is **empty** (`""`) when unset: it does **not** fall back, so legacy rows with no kind appear unclassified in metrics.

### Per-attempt trail

The flat columns describe only the attempt that ended the request. `attempts` (migration `078`) records the rest, written once when the request reaches a terminal state:

- One element per attempt, with the provider, the resolved model, the upstream status, the `error_kind`, a duration and a TTFT.
- Hedged probes that lost the race, and attempts abandoned when the race ended, are recorded too and flagged `hedged`. A hedged race is still **one** log row: the losers live in the trail, not in rows of their own.
- Candidates the circuit breaker or an in-flight limit refused before any request was sent appear with `attempt: -1` and the reason.
- A `breaker` verdict per attempt says what the circuit was told: `charge`, `noop`, `success`, `alive`, `skipped`, or `disabled`.
- `detail` carries at most 160 characters of the sanitized, credential-masked upstream error text, never request content. The terminal attempt has none, because its error is the row's own `error_message`.

This is the only place a 429 on attempt 0 of a request another provider then served is visible. The `attempt_provider_id` and `attempt_status` filters on the Logs API query it.

### Privacy Note

The proxy **never** logs prompt text, completion text, or any user content. The `request_hash` is a random identifier generated with `crypto/rand` (8 random bytes → 16 hex characters) - it is not derived from request content in any way.

### Dead Columns

The `request_id TEXT` column (from the initial schema) was never populated by the proxy and was always empty in the Logs API response. It was dropped in migration `030_drop_request_id.sql`.

> ⚠️ **The `prompt` column was removed in migration 027.** It was added in migration 006 but no application code ever wrote to it. The column has been dropped entirely - it no longer exists in the database schema.

## Proxy Overhead Breakdown

The `proxy_overhead_ms` field is decomposed into seven phases, measured in parallel with the actual provider request:

| Phase | DB Column | Description |
|-------|-----------|-------------|
| Parse | `parse_ms` | JSON parsing and request validation |
| Failover lookup | `failover_lookup_ms` | Resolving the failover group for `hotel/` requests (0 for direct provider requests) |
| Model lookup | `model_lookup_ms` | Resolving the model entity, checking model and provider enabled status, and building the ordered candidate list |
| Provider lookup | `provider_lookup_ms` | Finding the provider record in the database (excludes key decryption time) |
| Key decryption | `key_decrypt_ms` | Decrypting the provider API key (first call per 10-minute cache window; subsequent calls within the window are near-zero) |
| Settings read | `settings_read_ms` | Time spent reading runtime settings from the cached settings store (circuit breaker state, rate limits, etc.) |
| Dial | `dial_ms` | Full DNS + TCP dial time to the upstream provider |

The companion `cache_hits` JSONB column records, per component (`failover`, `model`, `provider`, `key`, `settings`), whether the lookup hit a prewarmed cache - useful for explaining why the same phase is sometimes fast and sometimes slow.

These represent pure proxy overhead - the time spent **inside** Model Hotel before and after the upstream call. You can use this to determine whether latency is coming from the provider or from the proxy itself.

The relationship between fields is:

- `proxy_overhead_ms = parse_ms + failover_lookup_ms + model_lookup_ms + provider_lookup_ms + key_decrypt_ms + settings_read_ms + dial_ms`
- `latency_ms = duration_ms - proxy_overhead_ms`

## Log Lifecycle and State Machine

### Request States

| State | Description | Transitions |
|-------|-------------|-------------|
| `pending` | Initial state when request is received | → `streaming` (on headers) or → `failed` (on error) |
| `streaming` | SSE stream in progress (headers sent, tokens flowing) | → `completed` (on success) or → `failed` (on error/interrupt) |
| `completed` | Request finished successfully (2xx status) | Terminal state |
| `failed` | Request failed (4xx/5xx status, timeout, or stale cleanup) | Terminal state |

### Logging Phases

#### 1. Initial INSERT (async)

When a request arrives, the proxy generates the row's UUID and request hash immediately and fires the INSERT off in a goroutine with a 5-second timeout, so the handler is never blocked by the write. A failed insert is logged but does not fail the request.

Fields written at this stage:

- `id` - UUID generated synchronously
- `request_hash` - Random 16-char hex ID
- `model_id` - From request body
- `streaming` - Boolean from request
- `virtual_key_name` - From context (if authenticated)
- `virtual_key_id` - From context (if authenticated)
- `failover_attempt` - `0` initially
- `state` - `"pending"`
- `endpoint_type` - Endpoint family (`chat` when unset)
- `owner_user_id` - Only for keyless dashboard rows (see the schema table)
- `client_ip` - Trusted-proxy-resolved client address (NULL when the ingest path had none)

All other columns are NULL at this point.

#### 2. UPDATE on headers (streaming) or on completion (non-streaming)

A single UPDATE statement writes everything else: the resolved provider and model, the status, the state, all seven overhead phases plus `cache_hits`, `response_header_ms` and `ttft_ms`, every token counter, `error_message`, `error_kind`, and the per-attempt trail. `latency_ms` is derived (`duration_ms - proxy_overhead_ms`) just before the write.

For **streaming** requests this runs twice: once when upstream headers arrive (`pending` → `streaming`) and once when the stream ends (`streaming` → `completed`/`failed`). For **non-streaming** requests it runs once (`pending` → `completed`/`failed`).

Because the row is visible from the first UPDATE onward, in-flight requests appear in the dashboard Logs table in real time, pulsing while they stream and settling as they finish. A request interrupted by a server crash or an unclean client disconnect stays in `pending` or `streaming` until the [stale cleanup](#stale-request-cleanup) marks it `failed`.

#### 3. Error handling

A failing request takes the same UPDATE path with `state = 'failed'`, a status code, an `error_message` and an `error_kind`. The message is capped at 10,000 characters at the point of writing, so no code path can slip a longer one past it, and it is passed through the content fence first (see [Error message limits](#error-message-limits)).

### SSE Events

Request lifecycle events are published to the event bus:

| Event Type | Severity | When | Metadata |
|------------|----------|------|----------|
| `request.started` | `info` | Once the model name is known, just after the initial INSERT | `request_id`, `model_id`, `streaming`, `state`, `owner_user_id` |
| `request.streaming` | `info` | Once a provider is chosen and the upstream stream starts forwarding | `request_id`, `model_id`, `provider_name`, `state`, `owner_user_id` |
| `request.completed` | `success` | On successful completion | `request_id`, `model_id`, `provider_name`, `state`, `status_code`, `owner_user_id` |
| `request.completed` | `warning` | On failure | Same fields; the error text is in the event's message, truncated to 200 characters |

`request.streaming` exists because a live dashboard row knows only the requested model until a provider is committed to; the event tells the dashboard to refetch the row and swap "Resolving" for the real provider mid-stream.

## Log Retention and Purge

### Automatic Retention

The `log_retention` setting controls how long logs are kept. When set, a background goroutine runs hourly and deletes rows older than the retention period from **both** `request_logs` and `app_logs`.

**Accepted values:** any Go duration string (`24h`, `48h`, `168h0m0s`, ...); the dashboard slider covers 0 to 30 days in whole-day steps and stores the value in hours. The legacy tokens `1d`, `1w`, and `1m` are still accepted, where `1m` means 30 days, not one minute; for a minute-scale window write `60m` or `1h`. Set to `0` (or any zero duration) or leave empty to disable automatic cleanup. A value that cannot be parsed is skipped and warned about once, not once per hour.

This setting can be changed at runtime via the Settings API (`PUT /api/settings`).

### Stale Request Cleanup

The `stale_request_timeout` setting (default: `30m`) controls how long a request can remain in `pending` or `streaming` state before being marked as `failed` with `error_kind = 'internal'` and the error `"request interrupted (stale)"`.

**Cleanup runs every 5 minutes** and applies two strategies in a single pass:

1. **Server-start-time check:** Any in-progress row that predates the current server process is definitively orphaned (the previous process is dead). This has zero false-positive risk.

2. **Age-based check:** Rows older than `stale_request_timeout` are marked failed. This catches in-process orphans (e.g. a panic skips the final update). The timeout is generous to avoid killing legitimate long-running streaming requests.

**Accepted values:** any Go duration; the dashboard slider covers 0 to 120 minutes in 5-minute steps. A value of `0` disables the whole periodic pass, including the server-start-time check, not just the age-based half.

Independently of that setting, the server runs one cleanup at startup, marking any in-progress row that predates the current process as `failed` with `error_kind = 'internal'` and the error `"request interrupted (server restart)"`.

Neither sweep touches `status_code`. A row still at `pending` keeps its empty status; a row already in `streaming` keeps the interim status it was given (typically `200`).

### Manual Purge

**API endpoints:** `DELETE /api/logs/purge` (request logs, admin only) and `DELETE /api/logs/app` (application logs).

Request body:
```json
{
  "older_than": "1h"
}
```

**Accepted values:** `1h`, `1d`, `1w`, `1m`, `all`. For `DELETE /api/logs/app` the body is optional; an empty body clears everything.

`DELETE /api/logs/app` purges in a fixed order: it first drains the asynchronous app-log writer, so entries already queued cannot flush back in behind the delete; then it deletes the rows; then it clears the in-memory ring buffer. A delete the database refuses answers `500` and leaves the ring buffer intact, so the live view still matches the rows that are still there. The reported `deleted` count is the number of database rows removed, or the number of ring entries cleared when no database is configured, never the two added together. A ranged purge matches rows on their insert time and ring entries on the entry's own timestamp, so at the cutoff itself the two can disagree by the writer's flush lag.

If that first drain does not finish, `DELETE /api/logs/app` answers `503 Service Unavailable` and nothing is deleted: no rows, no ring entries, no count. A healthy writer clears its queue in milliseconds however busy the gateway is, so a 503 means the writer is stalled behind an unreachable database or the process is shutting down; retry once the log history is moving again. The same answer covers a writer that is shutting down, since its queue is still draining into the database, and one that has already stopped: the stopped writer stays in place for the rest of the process lifetime, so a purge arriving after shutdown is refused rather than run against a queue nothing can confirm was drained. Retry the purge; once the queue is written out it succeeds, and if it keeps answering `503` the database is not keeping up with the log write rate.

Response for `DELETE /api/logs/purge`: `204 No Content` on success. `DELETE /api/logs/app` answers `200 OK` with `{"deleted": N}`.

## Viewing Logs

The dashboard has two log views, accessible from the **Logs** sidebar entry with sub-mode toggling.

### Requests Log

**API endpoints:** `GET /api/logs` (page/offset), `GET /api/logs/cursor` (keyset scrolling), `GET /api/logs/{id}` (one row, including its attempt trail).

Shows all proxy requests with:
- Sortable columns (timestamp, model, provider, status, latency, TTFT, tokens, etc.)
- Filters (date range, model, provider, status code, endpoint type, virtual key, client IP)
- Pagination (default 20 per page, max 200)
- In-flight request highlighting (rows pulse with animation while streaming)
- Click-through to provider/model details
- Status code color coding (green for 2xx, red for 4xx/5xx)

**Visibility is scoped by identity.** An admin sees every row and may narrow the view with `?owner_user_id=`. A non-admin sees only traffic from virtual keys they own, plus keyless dashboard rows stamped with their own user id; the scope is applied server-side to the listing, the count and the single-row fetch alike, so a row they do not own answers `404` rather than revealing that it exists. Rows with neither a key owner nor a stamped owner stay admin-only.

![Request Logs](screenshots/logs.png)

### App Logs

**API endpoints:** `GET /api/logs/app` (ring buffer or history), `GET /api/logs/app/cursor` (keyset scrolling), `DELETE /api/logs/app` (purge).

Shows the server's own application logs:
- Persisted to the `app_logs` database table
- Async batch writer for performance (buffers writes, flushes every 500ms or every 50 entries)
- Severity levels (`info`, `warning`, `error`, `debug`) - taken from the slog record where one exists, otherwise inferred from the line's wording
- Source attribution: the prefix before the first `": "` in the message (`proxy: forwarding ...` has source `proxy`), or a leading `[bracketed]` tag on lines that use one
- Two access modes:
  - **Ring buffer mode** (default) - returns the last N entries from an in-memory buffer of 500 (`?limit=` defaults to 500, maximum 1000), with optional `?after=` polling for live updates
  - **History mode** (`?history=true`) - queries the database with full filtering, pagination, and sorting

Application logs are also what the optional OTLP exporter ships when `OTEL_EXPORTER_OTLP_ENDPOINT` is set. Request logs are not exported that way; they stay in `request_logs` and are read through the Logs API and the Prometheus metrics.

![App Logs](screenshots/applogs.png)

#### Debug verbosity (`DEBUG_LOG` / `DEBUG_LOG_SCOPES`)

By default the server logs at Info and above. To get the per-request Debug
mechanics:

- **`DEBUG_LOG=true`** turns Debug on for **every** scope. Thorough, but it floods
  both stdout and this App Logs view at any real request rate.
- **`DEBUG_LOG_SCOPES=failover,resolve`** turns Debug on for **only** the named
  scopes - far more usable in production. It is ignored when `DEBUG_LOG=true`.

A scope is the source prefix before the first `:` in a log line (matched
case-insensitively). The scopes that actually emit Debug records are:

`access`, `admin`, `admin-chat`, `adminauth`, `anthropic`, `api`, `audit`,
`configsync`, `db`, `discovery`, `failover`, `frontdesk`, `models.dev`,
`paramrewrite`, `phrases`, `provider`, `prune`, `proxy`, `quota`,
`resolve`.

`proxy` is by far the most voluminous (the per-request mechanics), followed by
`frontdesk`, `discovery` and `resolve`; the rest are a handful of lines each.
`api` and `adminauth` are near-silent: their only Debug records come from the
shared JSON response writer, when a client hangs up or a handler times out
mid-response.

Both variables are startup-only (env vars, set via `.env` / compose). See
[[Configuration]] for the full table.

**A source is not the same thing as a scope.** These variables gate Debug
records only, so naming a source that emits none does nothing at all. Most App
Logs sources are in that position - `ratelimit`, `settings`, `backup`,
`webauthn`, `auth`, `model`, `virtual-keys`, `keycache`, `docker`, `stats`,
`system`, `applogs`, `events` and `version` all log at Info and above only, as
does `netguard` (the outbound connection guard behind SSO and alerting, see
[Security](Security#netguard-admin-configured-endpoints)), which logs at WARN
and above. Their lines appear in App Logs and in its source filter and are always
emitted; there is nothing to enable. The list above is the whole of what
`DEBUG_LOG_SCOPES` can act on.

## Filtering and Search

### Request Logs (`GET /api/logs`)

| Parameter | Description |
|-----------|-------------|
| `page` | Page number (default 1) |
| `per_page` | Results per page (1–200, default 20) |
| `model_id` | Filter by model ID (ILIKE match) |
| `provider_id` | Filter by provider UUID |
| `virtual_key_id` | Filter by virtual key UUID |
| `client_ip` | Filter by exact client address |
| `owner_user_id` | Admin only: restrict to one dashboard user's traffic. Ignored for non-admins, whose own scope is already forced. |
| `status_code` | Filter by HTTP status. Accepts exact codes, `4xx`, `5xx`, or `0` for in-progress/never-responded |
| `endpoint_type` | Filter by endpoint family: `chat`, `messages`, `embeddings`, `rerank`, `image`, `tts`, `stt` (unknown values are ignored) |
| `attempt_provider_id` | Filter on the attempt trail: requests in which this provider was tried at all, whoever served them in the end |
| `attempt_status` | Filter on the attempt trail: requests in which some attempt reached this upstream status |
| `from` | Start timestamp (RFC3339) |
| `to` | End timestamp (RFC3339) |
| `sort_by` | Sort column: `time`, `model`, `provider`, `status`, `tokens`, `tps`, `ttft`, `response_header_ms`, `duration`, `overhead`, `key`, `ip` |
| `sort_dir` | `asc` or `desc` (default `desc`) |

`attempt_provider_id` and `attempt_status` combine into a single containment test, so giving both matches requests where **one** attempt had that provider *and* that status, not two separate attempts. Unparseable values are ignored rather than rejected, as with the other filters.

`GET /api/logs/cursor` takes the same filters plus `cursor`, `direction` (`after`/`before`) and `limit` (1–200, default 20). It always sorts by time, so `sort_by` does not apply there.

**Special sorting behavior:**
- `provider`: NULL providers sort last, deleted providers (name NULL but ID present) sort second-to-last
- `tokens`: rows with no tokens at all sort after rows with tokens; among those, ones whose error mentions cancel/disconnect/context-canceled come before the rest
- `status`: within the same status code, errors with cancel/disconnect/context-canceled messages sort after other errors
- `key`: Deleted virtual keys (ID present but no matching row) sort last
- `tps`, `ttft`, `response_header_ms`, `duration`, `overhead`: zero values sort last
- `ip`: rows with no address sort last; addresses order lexicographically, which groups the same address together but puts `10.*` before `9.*`

|-----------|-------------|

| `source` | Filter by log source (e.g. `proxy`, `auth`, `discovery`) |
| `search` | Text search in message (ILIKE match) |
| `from` | Start timestamp (RFC3339) |
| `to` | End timestamp (RFC3339) |
| `page` | Page number (default 1) |
| `per_page` | Results per page (1–100, default 20) |
| `sort_by` | Sort column: `time`, `level`, `source`, `message` |

History mode returns a structured response including `entries`, `total`, `page`, `per_page`, plus `level_counts` and `source_counts` aggregates (cached for 5 seconds).

## How Model Name, Provider, and Token Counts Are Captured

### Model Name

`model_id` is the `model` field of the request body, exactly as the client sent it. For failover group requests (`hotel/xxx`) that display name is what is logged; the provider-specific model that actually served the request goes to `resolved_model_id`.

### Provider Resolution

`provider_id` is written once the proxy commits to a candidate and the upstream connection is established. Deleting a provider sets the column back to NULL (migration 010), so those rows show no provider at all rather than a dangling id; the Logs API's `'Deleted'` label is for the rarer case of a `provider_id` that no longer matches any provider row.

### Token Counts

Token counts come from the provider's own `usage` object, never from counting anything locally.

- **Non-streaming:** read straight out of the parsed upstream response.
- **Streaming:** accumulated as SSE chunks arrive. Some providers send usage only in the final chunk, others in every chunk, so the proxy keeps the last non-zero value it saw.
- **Large passthrough responses:** embeddings, image and audio responses over 8 MiB stream through without usage extraction, because buffering them would defeat the point. The row then records no token counts, but the request is still metered against the key's usage and TPM budget using an estimate of the prompt, so an oversized response is not a free one. The estimate never appears in the log as measured usage.

### DeepSeek Cache Tokens

DeepSeek providers may report `prompt_cache_hit_tokens` and `prompt_cache_miss_tokens` in the `usage` object. These are captured, written to the `tokens_prompt_cache_hit` and `tokens_prompt_cache_miss` columns, and exposed in the Logs API response.

## Error Logging for Failed Requests

### Error classification and status codes

Most failed requests are tagged with a machine-readable [`error_kind`](#request-log-schema), defined in `internal/proxy/reqerror.go`. The persisted `status_code` is **not** a fixed function of `error_kind`: it depends on *where* the request failed, as described under [Status code and error kind over a request's life](#status-code-and-error-kind-over-a-requests-life).

| `error_kind` | Status code | When | Example `error_message` |
|--------------|-------------|------|--------------------------|
| `validation` | 400 / 404 | Malformed body, missing model, invalid model format (400); unknown model / no enabled providers (404) | `"invalid request body"`, `"model 'xxx' not found"` |
| `auth` | 403 | Virtual key lacks access to any provider for the model | `"virtual key does not have access to any provider for this model"` |
| `provider_error` | upstream status, else 502 | Any upstream failure not placed more precisely, including every 5xx and an aggregator's own backend fault. Also the kind for a stream that ended without its `[DONE]` sentinel. | `"all 3 providers failed; last error: provider \"X\" returned HTTP 500 on attempt 2"` |
| `provider_model_gone` | upstream status | The provider says it no longer serves this model. Permanent: retire it or stop routing to it. | `"provider \"X\" no longer serves this model (attempt 1)"` |
| `provider_not_entitled` | upstream status (402, or a 429) | The account cannot pay for the model: empty balance, or a model outside the subscription. Retrying cannot help until someone tops up or changes plan. | `"provider \"X\" rejected the request for billing or plan reasons on attempt 1"` |
| `provider_bad_request` | upstream 400 | The provider understood the request and refused the payload, normally the wrong dialect for that upstream route rather than a provider fault | `"provider \"X\" rejected the request payload on attempt 1"` |
| `provider_saturated` | 429 | Alive and refusing on capacity (concurrency slots, RPM, TPM). Retry in seconds. | `"all 3 providers busy; last error: provider \"X\" is busy (rate limited at capacity) on attempt 3"` |
| `provider_quota_exhausted` | 429 | A usage window is spent (session, daily, weekly, or a coding-plan window). Retry after the window resets. | `"no available provider for hotel/glm-4.6; earliest retry in 45s"` |
| `provider_timeout` | 502 | TTFT probe or stall watchdog fired: provider connected but produced no output in time | `"provider \"X\" did not return a response in time on attempt 1"` |
| `failover_timeout` | 504 | The overall failover deadline expired | `"request timed out while waiting on provider \"X\""` |
| `retry_timeout` | 504 | The param-strip retry's deadline expired | `"retry without unsupported parameters timed out on provider \"X\""` |
| `client_disconnect` | 499 | The calling client hung up before we responded | `"client disconnected during attempt 1 to provider \"X\""` |
| `hedge_superseded` | 502 | The gateway cancelled this attempt because a faster hedged candidate won the race. The client is unaffected and is served by the winner, so this never appears as a terminal cause on its own. | `"attempt 2 to provider \"X\" was superseded by a faster hedged attempt"` |
| `internal` | 502 | Gateway-internal failure (e.g. could not build the upstream request). Also written by both stale sweeps. | `"internal error on attempt 1: …"`, `"request interrupted (stale)"` |

The 429 on the two capacity kinds is deliberate: every provider is alive, and OpenAI SDKs back off and retry on a 429 where they would give up on a 502. A `Retry-After` header carries the last provider's own ask, or the earliest instant a circuit reopens, capped at a minute. Turning the `failover_exhaustion_status_429` setting off restores the older `502` for both.

### Error message limits

Two different limits apply, for two different consumers:

- **In the database**, `error_message` is capped at **10,000 characters**, cut on a character boundary and marked with `…`. An upstream error body is sanitized to the same budget before it gets there. Both then pass through the content fence: any run of 16 or more characters the body shares with the request's own text (a provider quoting the prompt back) is replaced with `[content]`, in `error_message` and in every per-attempt `detail` alike.
- **In SSE events**, the `request.completed` message is truncated to **200 characters** with a `…` suffix, because it is a notification, not a record.

What the *client* receives is a third thing, and depends on the error class. A payload-class 4xx (a plain `400` and its kin, not `401`/`402`/`403`/`404`/`407`/`429`) forwards the provider's own error body with every provider key the gateway holds masked out (any row's key, enabled or not, not only the one being called), read under a 1 MiB cap. Anything else, meaning auth, billing, rate-limit, not-found and server-fault classes, or a body over the cap, gets a synthesized OpenAI-style envelope carrying the classified reason, because those upstream bodies can quote the operator's provider credentials or account details.

### Client Disconnect Handling

A client hanging up is detected through context cancellation on the request. The row is finished with `state = 'failed'`, `error_kind = 'client_disconnect'` and status `499`, which distinguishes it from a provider failure: nothing upstream went wrong, and the circuit breaker is not charged for it.

## Implementation Details

### Async INSERT with synchronous ID

The row's UUID and request hash are generated on the request goroutine, then the INSERT itself is queued. That way the later UPDATE always has an id to aim at without the client ever waiting on a database round trip, and a failed INSERT degrades to an UPDATE that touches no rows rather than to a failed request.

### Waiting for the INSERT

Updates on the hot path deliberately skip the wait, because it runs before the response body reaches the client and a cold INSERT could hold that up by as much as 5 seconds. That includes the interim `pending` → `streaming` write and the terminal writes on the latency-sensitive response paths. If such an update is terminal and touches no rows, it has lost the race with its own INSERT, so it then waits and retries once: without that repair the request would stay at `pending` with no status, no duration and no error until a stale sweep relabelled it. Every other update waits up front. An UPDATE that errors outright has no row count to trust and is left for the stale sweep.

### Log caching

The Logs API caches query results for 2 seconds to keep live polling off the database. The cache key includes the caller's owner scope, so an admin's unscoped page and a member's own page never share an entry. Responses carry `X-Cache: HIT` or `X-Cache: MISS`.
